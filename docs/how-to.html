操作指南

修改一个内置事件

以 builtin-01 为例：改源文件，重新生成模拟器和编辑器使用的数据，再确认路线和教学行为没有被改坏。

先找对文件

下文以 builtin-01 为例，修改其他事件时换成对应的 ID 即可。

只改 events/

events/ 是内置事件的唯一源文件；data/scenarios/ 和 data/editor/templates/ 都是生成结果，手改会在下次生成时被覆盖。也不要用编辑器保存来代替：编辑器只保证保留已支持的字段，而且用户保存不能覆盖 builtin-* 模板。

只改事件时，使用带 --events-only 的同步命令。不带该参数的完整同步会从 Unity 项目导入几何与场景格式，需要逐项审阅差异。

修改并重新生成

在仓库根目录依次执行：

  1. 编辑 events/builtin-01.json。

    字段含义见场景格式，驾驶者等浏览器扩展字段见车辆调度与信号。

  2. 重新生成浏览器事件、编辑器模板和车线提示。

    仓库根目录
    node tools/sync.mjs --events-only

  3. 查看生成结果的差异，确认只有预期的改动。

    仓库根目录
    git diff -- events/builtin-01.json data/scenarios/ data/editor/templates/ data/editor/lanes.json

检查事件行为

按改动范围选择检查，不必每次都跑全部。

  1. 运行该事件的教学行为检查（谨慎通过能到达终点、车辆出现时被遮挡或位于远处）。

    仓库根目录
    node tools/check_events.mjs builtin-01

    检查失败时，修正事件后回到上一节重新生成。

  2. 改了车辆路线的话，再跑路线检查和路线测试。

    仓库根目录
    node tools/check_routes.mjs
node --test test/routes.test.mjs

    如果还动了共享时序或接触判定，运行完整回归。

    仓库根目录
    npm test

  3. 在体验首页选择编号 01 的场景，亲自玩两遍：

    • 不观察、直接往前走——应当会遇到该事件的车辆；
    • 在路缘停下左右确认——应当能看到来车，等车过后安全到达终点。

  4. 在场景编辑器打开对应的内置模板，确认起点、终点和车辆路线与源文件一致。

提交前检查

行为确认无误后，检查差异和空白错误：

仓库根目录
git diff --check
git diff --stat

在变更说明里写清：为什么改、跑了哪些检查、哪些设备没有验证。

如果改动涉及共享流程或依赖，或者你拿不准影响范围，运行 npm run check：它依次执行类型检查、生成文档核对、完整测试和生产构建，部署 CI 用的也是这个入口。局部改动仍按 AGENTS.md 选最小检查即可。

推送 main 即部署

推送到 main 会通过 GitHub Actions 发布站点，推送前务必完成适用的检查。
